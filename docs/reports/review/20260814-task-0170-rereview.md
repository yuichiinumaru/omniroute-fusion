## New finding — disabled DB setting does not gate token refresh

**Severity:** High; production behavior / semantic contract
**Classification:** **NEW** (the previous env-only finding is resolved, but the resolver integration exposes a separate fail-open path)

`open-sse/services/tokenRefresh.ts::refreshQoderToken` now resolves the endpoint and credentials dynamically:

```ts
const tokenUrl = resolveQoderOAuthTokenUrl() || OAUTH_ENDPOINTS.qoder?.token;
const clientId = resolveQoderOAuthClientId() || PROVIDERS.qoder?.clientId;
const clientSecret = resolveQoderOAuthClientSecret() || PROVIDERS.qoder?.clientSecret;
```

However, the function never checks `resolveQoderOAuthEnabled()`. The resolver functions intentionally return DB/env endpoint and credential values independently, even when `qoderOAuthEnabled` is explicitly `false`. As a result, an operator can disable Qoder OAuth in the Database/UI while an existing refresh-token path continues making a network request. The focused probe reproduced this with one mocked fetch call and a non-null refresh result.

This conflicts with the task requirement that the UI setting dynamically enables/disables Qoder OAuth paths and with the existing disabled-refresh test's intended meaning. The current test named `refreshQoderToken skips refresh when OAuth is not enabled/configured` only covers the unconfigured case; it does not cover an explicit DB disable while environment fallback values are available.

**Required correction:** Make `refreshQoderToken` fail closed when `resolveQoderOAuthEnabled()` is false, before resolving or using endpoint/credential fallbacks; or make the shared resolver contract guarantee that an explicit false setting suppresses all Qoder OAuth values. Add a regression test with `qoderOAuthEnabled: false` plus populated environment values and assert no fetch occurs and the result is `null`.
