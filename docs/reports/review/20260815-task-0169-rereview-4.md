## Runtime call-chain audit

### Stored configured-proxy request path — residual gap

1. `resolveProxyForConnection()` reads a registry or legacy proxy object and returns a proxy config.
2. Callers pass that config to `runWithProxyContext()` or equivalent request plumbing.
3. `runWithProxyContext()` synchronously calls `proxyConfigToUrl(effectiveProxyConfig)`.
4. `proxyConfigToUrl()` and `normalizeProxyUrl()` reject literal private/local hosts, but do not await `assertValidProxyHost()` or any resolver.
5. `isProxyReachable()` then performs a TCP reachability check.
6. `proxyFetch()` calls `createProxyDispatcher()` and dispatches the request.

The TCP check is not a private-address/DNS-rebinding policy check. The dispatcher’s synchronous literal check is not a substitute for the asynchronous DNS guard. The direct probe confirms the ordering currently permits a stored rebinding hostname to reach both the probe and dispatcher fetch.

### Explicitly guarded egress helpers

`defaultEgressProbe()`, `diagnoseAllEgressIps()`, and `validateProxyPool()` still correctly call `assertValidProxyHost()` before egress probing or dispatcher construction. Their passing tests prove those helper entrypoints are fail-closed, but they do not cover normal request dispatch.

### Other dispatcher callers

The source audit still identifies direct calls from `patchedFetch`, `proxyFallback.testSingleProxy`, `MimocodeExecutor.getProxyDispatcher`, and route/helper paths. Route and persistence inputs are guarded. Fallback candidates are normally scraped IP literals, but the shared synchronous dispatcher boundary remains unsafe for any unchecked hostname supplied by a runtime caller.
