## Runtime call-chain audit

### Corrected stored configured-proxy request path

1. `resolveProxyForConnection()` reads registry or legacy proxy data.
2. Callers pass the config to `runWithProxyContext()`.
3. `runWithProxyContext()` extracts the host and awaits `assertValidProxyHost()`.
4. Only after successful DNS/private-address validation does it call `proxyConfigToUrl()`.
5. Only then does it run `isProxyReachable()` and the callback.
6. `patchedFetch()` performs a second asynchronous validation on the resolved proxy URL before `createProxyDispatcher()` and undici fetch.

The direct request-path probe confirms the intended ordering and fail-closed behavior.

### Remaining direct dispatcher path

`MimocodeExecutor.syncAccountsFromCredentials()` builds proxy URL strings from `providerSpecificData.accountProxies`, and `getProxyDispatcher()` passes those strings directly to `createProxyDispatcher()`. No `assertValidProxyHost()` call or equivalent asynchronous resolver runs at that boundary. A stored or credential-provided public-looking hostname can therefore pass the literal-only dispatcher checks and reach dispatcher construction.

This is narrower than the prior P0 gap: ordinary stored-proxy request context is now protected. It remains a lifecycle completeness issue because the task's proxy runtime surface includes direct per-account dispatch.
