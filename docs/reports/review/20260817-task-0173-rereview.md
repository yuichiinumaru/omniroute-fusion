## Findings

### High — signature set is not authoritative and the injection contract is incomplete

The reference implementation derives `FREEBUFF_SIGNATURE_TOOL_NAMES` as every `toolNames` entry that is not in `GENERIC_TOOL_NAMES`, plus `FREEBUFF_CUSTOM_TOOL_NAMES`. The local reference includes the four Composio meta-tools: `composio_manage_connections`, `composio_multi_execute_tool`, `composio_search_tools`, and `composio_get_tool_schemas`. The live connector omits all four. A legitimate Freebuff request whose only distinctive tools are Composio meta-tools can therefore be treated as foreign by the connector's own predicate and receive an unnecessary synthetic `think_deeply` tool.

The executor also injects `think_deeply` for generic-only and foreign toolsets. That may prevent the backend's name-based detector from downgrading, but it adds a tool the caller did not provide and does not establish that the caller can execute it. The tests assert that the transformed list contains the synthetic tool; they do not run the authoritative detector, cover Composio-only toolsets, or verify that tool schemas/call routing remain compatible after injection. This is a material improvement over the prior absence, but not a complete closure of the P0 contract.

### Medium — Zod is present but the schemas are permissive, not strict

`FreebuffDeviceCodeResponseRawSchema`, `FreebuffPollResponseRawSchema`, `FreebuffSessionAdmissionResponseSchema`, and `FreebuffAdmissionErrorPayloadSchema` all use optional fields and `.passthrough()`. As a result, undocumented fields are accepted and an empty object can validate at each raw boundary. The runtime adds fallback defaults for missing values, which may be intentional for upstream compatibility, but it does not satisfy a strict-schema requirement without an explicit compatibility rationale and targeted tests. The current tests label these schemas “strictly validates” while only checking a valid object and a primitive/null failure.

### Medium — provider error-rule scope is not wired into the executor's 429 response path

The Freebuff-specific registry correctly identifies capacity-deferred and IP-capped responses as provider-scope and ordinary rate-limited responses as connection-scope. However, `FreebuffExecutor.execute()` handles all chat 429s through the same `recordProviderFailure("freebuff", ...)` call and locally derives the reason from response text. The focused registry test proves matching in isolation, not that the executor applies the matched scope/cooldown. The shared provider breaker does open, so the prior “no runtime breaker integration” finding is closed, but the finer-grained rule behavior remains unverified.

### Medium — repository-wide lint remains red; runtime coverage remains mocked/unit-only

The required focused tests, core typecheck, and scoped lint are green. The literal repository-wide lint command still fails on seven unrelated `visual-reference` errors, including an impure `Math.random()` render call, synchronous state in an effect, undefined `PrismDivider`, and an unescaped apostrophe. No live endpoint or production smoke test was used; this is appropriate for safety, but the evidence does not establish route-level OAuth persistence or production entrypoint behavior.
